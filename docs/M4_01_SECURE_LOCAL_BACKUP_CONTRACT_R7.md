## 0. Independent Audit Summary (R1 → R2 Critical Fixes)

This R2 revision directly resolves the following cryptographic, database, storage, and crash-recovery flaws identified during independent security review of R1:

1. **Eliminated Pre-Authentication JSON Parsing & Canonicalization Ambiguity (§4):** Replaced R1's underspecified "canonical UTF-8 JSON header" with a deterministic **90-byte fixed-layout binary header** (`MCBK v1`). This removes all pre-AEAD JSON parser attack surfaces (duplicate keys, whitespace/Unicode escape variance, malformed UTF-8) across Dart, Kotlin, and Python.
2. **Specified Concrete KDF Bounds, Native Execution, and Low-RAM Protection (§3, §4, §6):** Proposed native Argon2id, explicit resource caps and available-RAM checks. **R3 correction:** resource checks and zeroization reduce risks but cannot guarantee avoidance of OOM or removal of all secret copies; accepted work-factor combinations are restricted to tested profiles rather than every in-range tuple.
3. **Hardened Password Handling & Key Zeroization (§3):** Defined password length strictly by Unicode scalar values (`runes.length >= 12`), rejected whitespace-only passphrases, and required best-effort zero-filling of mutable secret buffers. **R3 correction:** Dart `String`/GC copies cannot be promised to be zeroized.
4. **Bounded Memory via File-Streamed Single-Tag AES-256-GCM (§5, §6):** Replaced in-memory full-payload buffering (which caused `~164+ MiB` heap spikes for `64 MiB` payloads) with native/FFI file-streamed single-tag AES-256-GCM I/O (`<= 64 KiB` chunk buffers).
5. **Hardened SQLite Inspection Against Crafted/Malicious Payloads (§6):** Added mandatory SQLite defensive controls before inspecting any decrypted staging candidate (`SQLITE_OPEN_READONLY`, `trusted_schema = OFF`, `defensive = ON`, `writable_schema = OFF`, triggers/views/extensions disabled, strict `sqlite_master` whitelist against schema v5, and a bounded page-size/count check). **R3 correction:** no unsupported combined `PRAGMA page_size * PRAGMA page_count` SQL.
6. **Closed Drift Background Isolate & WAL/SHM Sidecar Race Conditions (§5, §6):** Specified explicit isolate shutdown confirmation + open file-descriptor verification before Phase B file operations, mandatory `PRAGMA wal_checkpoint(TRUNCATE)` and removal/archival of residual `-wal`/`-shm` files (preventing old WAL replay onto a newly restored DB), and exclusion/preservation of static `DrugCatalog` reference data.
7. **Specified `fsync`-Durable Journal Protocol & Pre-Boot Recovery Bootstrapper (§6):** Defined the journal and mandatory pre-open recovery. **R3 correction:** R2's `OLD_SAVED` recovery used a potentially destructive rename of the only rollback file and was not repeatable if recovery itself crashed. R3 retains an immutable rollback source, uses retryable copies, and verifies committed/recovered DBs before cleanup.
8. **Specified Android SAF Partial-Write Cleanup & `no_backup` Staging Isolation (§5, §6, §7):** Defined exact `ContentResolver` stream sync, byte-count verification, `DocumentsContract.deleteDocument` best-effort cleanup on SAF failure, `OpenableColumns.SIZE` + streaming byte cap on import, `getNoBackupFilesDir()` staging isolation, and explicit Android 11 (`fullBackupContent`) + Android 12+ (`dataExtractionRules` for both `cloud-backup` and `device-transfer`) XML rules.

### 0.1 Independent R2 → R3 correction log (blocking issues)

1. **Repeatable rollback and crash ordering:** retain a validated rollback master across *every* recovery attempt; journal `COMMITTED` durably before deleting it; verify even `VERIFIED`/`COMMITTED` states; fail closed if both copies are bad (§6).
2. **Safe cleanup ordering:** first run journal recovery, then sweep orphan staging; cleanup must never destroy candidate or rollback data required by an interrupted transaction (§§1, 5–6).
3. **SQLite correctness:** use individually supported `PRAGMA page_size`/`PRAGMA page_count` queries, a deliberately hardened SQLite connection before preparing schema SQL, pinned schema inventories for each source version, and fixture-tested migrations; do not open unvalidated databases through Drift (§6).
4. **SAF durability:** Android document providers do not offer a general atomic-write or remote-fsync guarantee; use a supported `ParcelFileDescriptor` where available, handle unsupported sync, read back and compare a streaming SHA-256 when possible, and distinguish verified from unverified exports (§5).
5. **Actual application alignment:** at baseline v5 there are exactly **17** Drift tables; `DrugCatalogEntry`, `DrugCatalogVersion`, `AlertInstance`, and persisted `DoseOccurrence` tables are PRD targets, not implemented SQL tables. No Riverpod or WorkManager dependency was established in the inspected baseline (§§2, 6).
6. **Worker and notification boundary:** a confirmed replacement can outlive a process kill before Android alarms have been reconciled; make the restart reconciler durable/idempotent and report partial notification states honestly (§6).
7. **Crypto/resource limits:** restrict recognized KDF profiles, acknowledge Kotlin/FFI availability and password zeroization limits, validate file-cap calculations, and add corresponding failure-injection tests (§§3–4, 8).

### 0.2 Independent R3 → R4 audit & fix log (final hardening)

1. **Pre-KDF Binary Header Overflow & `DateTime` Bounds (`§4`):** Fixed signed 64-bit integer overflow risk on `ciphertext_length` (`uint64BE`) by enforcing `4096 <= ciphertext_length <= 67108864` **prior** to evaluating `121 + ciphertext_length == actual_file_size`, bounded `created_utc_epoch_ms` to Dart `DateTime` safe limits (`1 .. 8640000000000000`), and aligned `§4` KDF field documentation with `§3`'s strict approved tuple allowlist.
2. **Crash-Recovery Completeness for `install.ready`, `old_absent`, and Journal/Reconcile Storage (`§6.6–6.10`):** Added explicit cleanup of stray `install.ready` and `old_reinstall.ready` temporary files during `OLD_SAVED` recovery; resolved a false brick condition on fresh-install (`old_absent = true`) crashes occurring between atomic rename and `NEW_INSTALLED` journal commit by matching `candidate_sha256`; and pinned both `restore_journal.json` and `reconcile_pending.flag` to `fsync`-committed, `SHA-256`-verified files in `getNoBackupFilesDir()/backup_journal/` rather than asynchronous `SharedPreferences`.
3. **Android SAF Truncate Mode & `FLAG_SUPPORTS_DELETE` Guard (`§5.6`, `§8` Test 44):** Specified `"wt"` (write-truncate) mode on `openFileDescriptor(uri, "wt")` with explicit fallback to `openOutputStream(uri, "wt")` / `openOutputStream(uri)` for stream-only cloud providers, and mandated querying `DocumentsContract.Document.COLUMN_FLAGS` for `FLAG_SUPPORTS_DELETE` before invoking `DocumentsContract.deleteDocument`.
4. **SQLite Authorizer (`ATTACH` Block), `sqlite_sequence` Allowlisting, and Bound `VACUUM INTO` (`§5.2`, `§6.3–6.4`):** Mandated `sqlite3_set_authorizer` on the untrusted validation connection to block `SQLITE_ATTACH` / `SQLITE_DETACH` (since `SQLITE_DBCONFIG_DEFENSIVE` alone does not prevent read-only `ATTACH`), standardized on `sqlite_master`, explicitly included `sqlite_sequence` and `sqlite_autoindex_*` in schema allowlists, mandated bound parameter `VACUUM INTO ?` with `busy_timeout = 5000 ms`, and isolated staged migrations from `AppDatabase.beforeOpen` production side effects.
5. **Concrete Native `SafeScheduledNotificationBootReceiver` Architecture (`§2`, `§6.10`, `§8` Test 49):** Replaced the generic receiver-gating requirement with an explicit manifest override (`SafeScheduledNotificationBootReceiver` replacing `com.dexterous.flutterlocalnotifications.ScheduledNotificationBootReceiver` via `tools:node="remove"`) that synchronously checks `restore_journal.json` and `reconcile_pending.flag` before delegating to `FlutterLocalNotificationsPlugin.rescheduleNotifications(context)`.
6. **Expanded Test Matrix & Primary Documentation References (`§8`, `References`):** Updated Tests `5`, `27`, `38`, `41`, `43`, `44`, `45`, and `49` to cover every newly closed edge case and added primary SQLite `sqlite3_set_authorizer` and Android `DocumentsContract` citations.

### 0.3 Independent R4 → R5 corrections (implementation-blocking)

1. **Native boot receiver compile-time failure:** On the actual pinned `flutter_local_notifications: 23.0.2` Java implementation, `FlutterLocalNotificationsPlugin.rescheduleNotifications(Context)` is **package-private** (`static void` without `public`); an app-package receiver cannot call it directly as R4 prescribed. R5 delegates through the plugin's **public `ScheduledNotificationBootReceiver.onReceive(context, intent)`** only after native fail-closed marker checks. This preserves the plugin's own rescheduling logic without relying on inaccessible internals. Compile and device-test against the **exact version 23.0.2**, not a hypothetical public API (§§2, 6.10, 8).
2. **Preview-to-commit TOCTOU:** R4 showed the user a live-data comparison but did not ensure the dataset was unchanged by a legitimate write between preview and final replacement. R5 binds confirmation to a consistent live logical-data fingerprint and rechecks it under the Phase B lifecycle lock; any change cancels replacement and requires fresh preview/consent (§6.5–6.6, Test 51).
3. **WAL-sidecar rollback ordering:** R4's `OLD_SAVED` recovery renamed the old DB into place **before** removing residual sidecars, leaving a crash window where WAL from the newly installed DB could accompany the restored original. R5 requires verified handle closure and deletion/fsync of safely disposable sidecars **before** overwriting the DB filename and retains the immutable rollback master throughout (§6.9, Test 39).
4. **Validated R4 fixes retained:** R4's 90-byte binary framing, signed/unsigned length guard, tested parameter-bound `VACUUM INTO ?` (works on a read-only SQLite connection), source-version schema gates, native authorizer, SAF `wt`/readback, journal durability, and R4's 49 tests are preserved and extended. The revised inventory contains **51** tests.

### 0.4 Independent R5 → R6 audit & fix log (runtime & edge-case completion)

1. **SQLite Authorizer Ordering & Operation Allowlist (`§6.3`, `§6.4`):** Fixed a self-blocking defect where `PRAGMA mmap_size=0`, `PRAGMA cell_size_check=ON`, and `PRAGMA writable_schema=OFF` were not in the authorizer's read-only PRAGMA list, and explicitly permitted `SQLITE_SELECT`, `SQLITE_READ`, and safe built-in scalar/aggregate `SQLITE_FUNCTION` operations required internally by `PRAGMA integrity_check(10)` and `PRAGMA foreign_key_check` (as well as Drift `Migrator.alterTable` DDL/DML during `v1..v4 -> v5` staged migration) while keeping `SQLITE_ATTACH`, `SQLITE_DETACH`, triggers, views, virtual tables, and `load_extension` strictly denied.
2. **Android SAF `ParcelFileDescriptor` Lifecycle & `closeWithError` (`§5.6`, `§8` Test 44):** Mandated explicit `ParcelFileDescriptor.close()` after closing the wrapping `FileOutputStream` (preventing `CloseGuard` leaks and delayed provider commit) and `ParcelFileDescriptor.closeWithError(...)` on write/sync failure so pipe-backed `DocumentsProvider`s discard partial transfers rather than committing on normal EOF.
3. **Background Dart Entrypoint Recovery Guard (`§2`, `§6.9–6.10`, `§8` Test 49):** Mandated calling `await RestoreRecoveryBootstrapper.runBeforeAppStart()` (guarded by an idempotent process-wide lock) at the entry of **every** Dart/Flutter entrypoint—including `@pragma('vm:entry-point')` background notification action isolates—before opening `AppDatabase`, and clarified that pending `ScheduledNotificationReceiver` alarms firing after process death without reboot cannot mutate reconciled database state.
4. **SAF Zero-Byte Early Reject & Conditional `sqlite_sequence` Check (`§6.1`, `§6.5`, `§8` Tests 38 & 51):** Rejected `OpenableColumns.SIZE == 0` immediately on import (treating only `null` or `< 0` as unknown provider size) and guarded the `sqlite_sequence` query behind an explicit `sqlite_master` existence check so databases without `AUTOINCREMENT` tables do not raise `no such table: sqlite_sequence`.

### 0.5 Independent R6 → R7 corrections (verified runtime/transaction blockers)

1. **Android AES-GCM is not necessarily constant-memory (`§3`, `§5`, `§6`, Tests 8/52):** Android's actual Conscrypt `OpenSSLAeadCipher.updateInternal` appends input to an expanding buffer and returns zero output until `doFinal`. Therefore repeatedly calling Java `Cipher.update` with 64 KiB chunks **does not prove 64 KiB peak memory**, and can violate the R6 64 MiB low-RAM requirement. R7 requires a reviewed, genuinely incremental native/FFI GCM engine, bounded **total** buffering (not merely input chunk size), quarantined pre-tag plaintext, and measured heap/native RSS limits. Java `Cipher` is permitted only if the exact device/provider implementation passes an equivalent measured end-to-end bound, not by assumption.
2. **Dart isolate-local locks do not serialize other engines (`§2`, `§6.6`, `§6.9–6.10`, Test 53):** A Dart static/mutex is local to its isolate; independently initialized background engines do not share it. R7 mandates an empirically verified **native/OS-backed cross-isolate/process lifecycle lock** and one authoritative recovery owner. Background callbacks must first obtain a native recovery-complete guard or defer/drop DB-dependent work safely; they must not independently race the main-boot rollback or construct `AppDatabase` while restore is incomplete.
3. **SQLite foreign-key PRAGMA ordering (`§6.4`, Test 54):** `PRAGMA foreign_keys=ON/OFF` has **no effect inside an open `BEGIN`/`SAVEPOINT`**. R7 requires schema-specific, fixture-tested migration policy with any required foreign-key setting chosen and confirmed **before** starting the transaction, and full `foreign_key_check` afterwards; no unverified blanket assumption that Drift `Migrator.alterTable` works under an arbitrary authorizer/transaction arrangement.
4. **SAF descriptor ownership and error signaling (`§5.6`, Test 44):** R7 clarifies one ownership/close strategy and error-before-successful-close ordering. `closeWithError` is a best-effort signal only for supporting providers/reliable pipes; it is not a universal guarantee that a remote provider deleted a partial file.

R7 retains the complete R6 binary format, 17-table/SQLite checks, Phase A/B consent and rollback state machine, and previous 51 tests; the inventory is extended to **54** targeted verification cases.

## 1. Outcome and non-negotiable invariants

Deliver offline, password-protected backup and **explicit full-device-data replacement** restore for all local user profiles, medication plans, events, stock-ledger history, health observations, follow-up visits/tasks, questions, and app settings.

1. **No account, internet, backend, or subscription required.** Backup and restore work with airplane mode enabled.
2. **No silent deletion or overwrite.** Any failed/cancelled/wrong-password/incompatible/corrupt **Phase A** import causes zero active-DB or Android-reminder mutation. After explicit Phase B approval, an interruption may require a rollback and notification reconciliation on next launch; guarantee **eventual restoration of a verified old or new dataset**, not physically zero interim mutations across process death.
3. **No merge in v1.** Restore replaces the entire local dataset only after explicit confirmation showing its effects; preserve primary keys/event history. Future merge requires a separate conflict/idempotency design.
4. **No plaintext backup in shared/public storage.** Share/export only authenticated ciphertext. Unencrypted staging is limited to `getNoBackupFilesDir()` and short retention. Remove it on success, ordinary failure and cancellation; **on cold launch run durable restore recovery FIRST**, then sweep only staging orphans **not referenced by an active restore journal**. On flash media, file unlinking/zero-fill is not a guaranteed forensic secure erase; rely on Android filesystem protection and account for M4-02 encryption at rest.
5. **Do not claim the existing SQLite database is encrypted.** Current `AppDatabase()` uses `driftDatabase(name: 'medication_companion_m1')`, schema version **5**, without demonstrated SQLCipher-at-rest protection. Encrypted export does not fix that separate privacy gap.
6. **No medical interpretations, dose edits, or inferred data.** This package only reproduces stored user data and reconciles existing local reminders and persistent alerts after success.
7. Preserve user data across software upgrades and database migrations. Reject unsupported future backup/schema versions with an explicit explanation, never silently downgrade.
8. Warn accurately: without a backed-up file or online sync, guest data can be irretrievably lost on app uninstall/device loss. Forgotten backup password cannot be recovered by the developer.

## 3. Threat model and cryptographic choices

**Threats in scope:** stolen/exported `.medbackup` file, wrong password, offline password guessing, tampered/truncated/replayed input, attacker-controlled length/KDF fields, huge file/zip/SQLite-page bomb, crafted malicious SQLite triggers/views/schemas/ATTACH statements inside an encrypted file, mid-restore crash/process kill, low disk space, low RAM OOM during KDF, stale WAL/SHM sidecars, stale notification jobs, old schema, accidental overwrite of a different profile.

**Out of scope:** compromised/rooted Android/OS, malicious keyboard, screen recording, a weak password chosen by the user, recovery of a forgotten password. The app must not promise protection against these.

- **Symmetric Authenticated Encryption:** **AES-256-GCM** with a 12-byte (96-bit) fresh cryptographically random nonce (e.g. Dart **`Random.secure()`** or native Android **`java.security.SecureRandom`**, from a verified CSPRNG) and 16-byte (128-bit) authentication tag.
  - To reduce `OutOfMemoryError` risk on low-RAM Android devices when processing up to `64 MiB`, AES-256-GCM encryption and decryption **must** use a **genuinely incremental**, reviewed native/FFI cipher implementation (e.g. correctly managed BoringSSL/OpenSSL EVP `EncryptUpdate` / `DecryptUpdate` and `Final` with the single GCM tag). Bound **all** input, output, native and managed staging buffers—not only the file read size—to `<= 64 KiB` chunks plus documented small constant overhead. **Do not assume Java `Cipher.update` streams GCM:** Android Conscrypt's `OpenSSLAeadCipher` buffers accumulated input in `updateInternal` and emits output at `doFinal` on examined implementations; a loop reading 64 KiB can still accumulate the entire 64 MiB payload in memory. A Java/JCE or `cryptography_flutter` adapter is acceptable **only after inspecting the exact backend and measuring its real peak memory** on Android x86_64 and ARM64. A streaming decrypter may temporarily emit **unauthenticated** plaintext *only* into quarantined private staging; never parse, open, publish, or accept that file before final tag verification, successful close and defensive validation. On failure wipe ephemeral key buffers, close handles and remove the quarantined file best-effort. Reject an implementation that only buffers then authenticates all 64 MiB at once. Android OS OOM kills cannot be ruled out; test a measured device resource budget.
- **Cross-Device Password KDF:** **Argon2id**, default export profile `memory = 65536 KiB (64 MiB)`, `iterations = 3`, `parallelism = 1`, `output = 32 bytes (256 bits)`, with a fresh 16-byte (128-bit) random salt per export.
  - **Audited Native/FFI Execution:** Select and pin a tested native Argon2id implementation with maintained Android ABI support (`arm64-v8a`, emulator `x86_64`) and suitable lifecycle/cancellation behavior. No unbenchmarked pure-Dart fallback in released builds; latency and ANR claims require measurement, not assumptions.
  - **Pre-Allocation Absolute Bounds & Approved Tuple Allowlist:** Reject immediately if `m < 19456` or `m > 262144` KiB, `t < 2` or `t > 20`, or `p < 1` or `p > 4`. These are defensive parser caps, **not** independent permission to accept every tuple. For **MCBK v1**, accept only explicitly tested approved parameter tuples: **required `(65536, 3, 1)`**; optional low-memory `(19456, 4, 1)` **only after independent strength/performance sign-off and test vectors**. Reject all other combinations until a versioned reader policy authorizes them. Export must use one approved tuple and encode it exactly.
  - **Device Memory Guard:** Query `ActivityManager.MemoryInfo` (`availMem`, `lowMemory`) plus process-specific limits, apply an empirical safety margin, run on bounded-concurrency native workers, and catch native allocation failures. This reduces but **cannot eliminate** OS OOM risk. Fail gracefully where possible (`حافظه رم دستگاه برای بازگشایی این فایل پشتیبان کافی نیست`) and verify by low-memory device tests.
  - **Work-Factor Policy:** Benchmark both approved profiles against minimum supported phones. Never silently downgrade to the optional low-memory profile; identify it in the UI and require explicit user consent if it is enabled.
- **Password Entry & Memory Hygiene:**
  - Minimum **12 valid Unicode scalar values** (`password.runes.length >= 12` after validation), rejecting whitespace-only strings (`password.trim().isEmpty`). Reject ill-formed surrogate input whose UTF-8 encoding could silently substitute a replacement character.
  - Double-entry confirmation on export, mask/reveal toggle, **no implicit trimming and no Unicode normalization** (encode exact UTF-8 bytes of the raw string so cross-device Persian and emoji passphrases round-trip deterministically).
  - No hardcoded/default password; zero persistence, logging, crash-reporting, or analytics for passwords, derived keys, salts/nonces tied to secrets, or plaintext medical data.
  - **Best-Effort Key Zeroization:** Wipe all mutable password-byte/key/scratch buffers in `finally` **only after the final encryption/decryption/verification operation** and after native cipher context disposal; use native secure-clear for native memory and avoid needless copies. Dart immutable `String`, garbage collector, JNI or library-internal copies cannot be reliably zeroized; **never promise guaranteed complete in-RAM erasure**.
  - Warn user prominently before backup creation that a strong passphrase is essential and irrecoverable if lost.
- **Crypto Implementation Candidate:** Audited native-backed `cryptography` + `cryptography_flutter` **only if its concrete Android GCM implementation demonstrably supports bounded-memory incremental decryption**, or audited C/Rust FFI (`libsodium` / `argon2` + BoringSSL/OpenSSL incremental GCM) pinned to exact hashes/versions. A provider that internally buffers the entire ciphertext is disallowed for this v1 size/resource contract. No custom AES/Argon implementation, `Random()` salts, fixed IVs, homemade XOR, or reversible password storage.
- **Keystore Separation:** Device Keystore key is **not** used as the sole backup key because backups must be recoverable on a replacement device. Keystore-based encryption of the *live* DB is a separate design (`M4-02`).

## 4. Binary file format: `MCBK v1` (deterministic fixed-layout binary contract)

Do not use a plain `.db` or rename a database file to pretend it is encrypted. To eliminate pre-authentication JSON canonicalization bugs, duplicate-key smuggling, and parser vulnerabilities, `MCBK v1` uses a **deterministic fixed-layout 90-byte binary header** (121 bytes total framing overhead):

```
Offset  Size      Field                     Type / Value
------  --------  ------------------------  --------------------------------------------------
0       4 bytes   magic                     ASCII "MCBK" (0x4D 0x43 0x42 0x4B)
4       1 byte    envelope_version          uint8 = 1
5       2 bytes   header_length             uint16BE = 90 (must equal 90 for envelope_version = 1)
--- Begin Fixed Binary Header (90 bytes, offsets 7..96) ---
7       21 bytes  app_id                    ASCII "medication-companion\0" (exact 21 bytes)
28      16 bytes  backup_id                 random 128-bit identifier (CSPRNG)
44      8 bytes   created_utc_epoch_ms      int64BE UTC ms since epoch (1 .. 8640000000000000)
52      4 bytes   database_schema_version   uint32BE (5 in baseline; allowed 1..5 in v1)
56      1 byte    cipher_id                 uint8 = 0x01 (AES-256-GCM)
57      1 byte    kdf_id                    uint8 = 0x01 (Argon2id)
58      4 bytes   kdf_memory_kib            uint32BE (65536; hard cap 19456..262144 + §3 tuple)
62      4 bytes   kdf_iterations            uint32BE (3; hard cap 2..20 + §3 tuple)
66      1 byte    kdf_parallelism           uint8 (1; hard cap 1..4 + §3 tuple)
67      16 bytes  salt                      random 128-bit salt (CSPRNG)
83      12 bytes  nonce                     random 96-bit nonce (CSPRNG)
95      2 bytes   reserved_flags            uint16BE = 0x0000 (must be 0 in envelope_version = 1)
--- End Fixed Binary Header ---
97      8 bytes   ciphertext_length         uint64BE (bounded: 4096 <= m <= 67108864 [64 MiB])
105     m bytes   ciphertext                AES-256-GCM ciphertext of SQLite snapshot
105+m   16 bytes  auth_tag                  AES-256-GCM 128-bit authentication tag
121+m   0 bytes   EOF                       exact file end; zero trailing bytes permitted
```

- **AES-GCM AAD (105 bytes):** Exact raw bytes `[0 .. 104]` (`magic || envelope_version || uint16BE(header_length) || header_bytes || uint64BE(ciphertext_length)`). Mutating any header byte, reserved flag, or declared length fails authentication unconditionally.
- **Metadata Privacy:** Header contains zero user names, drug lists, phone numbers, or plaintext health data; `created_utc_epoch_ms` and `database_schema_version` are intentionally visible metadata.
- **Pre-KDF Fail-Closed Validation:** First obtain the exact local ciphertext file size (`actual_file_size >= 121`). Read `ciphertext_length` (`uint64BE`) and **first** validate `4096 <= ciphertext_length <= 67108864` (preventing signed 64-bit integer overflow in Dart when `ciphertext_length >= 2^63`); then reject if `121 + ciphertext_length != actual_file_size`. Verify `magic == "MCBK"`, `envelope_version == 1`, `header_length == 90`, exact `app_id` bytes, `cipher_id == 0x01`, `kdf_id == 0x01`, `1 <= created_utc_epoch_ms <= 8640000000000000` (Dart `DateTime` safe range), `reserved_flags == 0`, `1 <= database_schema_version <= 5`, absolute KDF bounds **and an approved v1 parameter tuple from §3**. This **pre-authentication header is untrusted**, regardless of syntactic validity; do not construct or display `DateTime`, `created_utc_epoch_ms`, `backup_id`, or schema as established facts until GCM verification succeeds.
- **Format Compatibility Fixtures:** Publish deterministic layout/offset and cross-implementation known-answer vectors with a fixed test-only password/salt/nonce/plaintext. Never reuse deterministic salt or nonce for real backups. Check encrypted frame for accidental UTF-8/JSON use, endianness differences, signed-64-bit overflow, exactly 105 AAD bytes, and exact EOF.
- **Payload Verification:** The decrypted payload is a single, consistent SQLite database snapshot (`user_version` matching `database_schema_version`). GCM authentication **and** SQLite defensive schema/integrity/foreign-key checks are both mandatory; neither replaces the other.
- **Forward Compatibility:** New format/algorithm/schema transitions require explicit versioned readers (`envelope_version = 2`, etc.), known test vectors, and migration tests; non-zero `reserved_flags` or unknown versions cause immediate rejection.

## 5. Export pipeline (no live-data mutation)

1. **User Consent & Destination Selection:** On `بیشتر ← پشتیبان و بازیابی ← ساخت پشتیبان رمزگذاری‌شده`, display clear warnings regarding health data sensitivity, scope (covers local database; excludes bundled drug catalog and external attachments if added later), and unrecoverable passphrase. User enters/confirms passphrase (`runes.length >= 12`) and picks a destination via Android Storage Access Framework (SAF) `ACTION_CREATE_DOCUMENT` (default filename `medication-backup-YYYYMMDD-HHMMSS.medbackup`).
2. **Concurrency Serialization & Consistent Snapshot:** Acquire exclusive `BackupRestoreMutex` (serializing export against concurrent exports, restore operations, and background cleanup). Budget space on `getNoBackupFilesDir()` for the **snapshot + ciphertext + verification copy** (+16 MiB margin); refuse a low-space export **before** writing. Create a fresh, previously nonexistent private snapshot path inside `<app_no_backup_dir>/backup_staging/`. Open an isolated read-only/snapshot SQLite connection to the **actual** Drift SQLite file with `busy_timeout = 5000 ms` and execute a strictly parameter-bound `VACUUM INTO ?` outside any active transaction (never string-interpolate filenames); if `VACUUM INTO ?` is unsupported, use the SQLite Online Backup API (`sqlite3_backup_init/step/finish`) **only when separately tested**. A dedicated connection observes committed WAL frames; snapshot consistency does **not** imply UI writes must be blocked for the entire export. Never copy a live `*.db` byte-for-byte during writes.
3. **Snapshot Integrity & Size Verification:** On the isolated staging snapshot, verify `PRAGMA integrity_check(10)` returns a single row `'ok'`, `PRAGMA foreign_key_check` returns empty, and `PRAGMA user_version == 5` (matching current app schema version). Verify snapshot byte size is `>= 4096` and `<= 67108864` (`64 MiB`) **before** encryption; if over `64 MiB`, abort cleanly with an explicit size-limit message. Capture table row counts in memory for verification only (never log patient-level content).
4. **Streamed Key Derivation & Encryption:** Check available device RAM, derive the 32-byte key via an approved native Argon2id tuple with a fresh 16-byte salt, and stream-encrypt the snapshot file into `<staging_dir>/<uuid>.medbackup.part` using a reviewed, **actually incremental and bounded-memory** native/FFI AES-256-GCM implementation and fresh 12-byte nonce with 105-byte AAD. The 64 KiB read loop alone is insufficient evidence of constant memory (§3); instrument the chosen provider's entire native/Java/Dart memory use. It must authenticate the complete single-tag stream before accepting plaintext and must never expose an unauthenticated decrypted candidate to SQLite. Only wipe required key buffers **after** the encryption + round-trip verification lifecycle ends.
5. **Pre-Publish Round-Trip Verification:** Before touching the user's SAF destination URI, re-parse the exact **105-byte AAD/framing prefix**, ciphertext length and **separate trailing 16-byte tag**, then incrementally stream-decrypt/authenticate into a second **quarantined** private verification file with the entered passphrase, with measured bounded native and managed buffering. Only after successful **final** tag verification and file close inspect SQLite integrity and row counts against the original snapshot. On failed authentication never open that file as SQLite and unlink it best-effort. Unlink plaintext verification file on all paths; flash block erasure is not guaranteed.
6. **SAF Publish, Verification & Partial-File Guard:** `ACTION_CREATE_DOCUMENT` returns a provider-controlled `content://` URI; there is **no universal atomic commit or remote durability guarantee**. Stream the ciphertext only. Prefer `ContentResolver.openFileDescriptor(uri, "wt")` (write-truncate) where supported, with **one explicit descriptor ownership strategy**: use `ParcelFileDescriptor.AutoCloseOutputStream` (whose close owns `pfd.close()`), **or** a raw `FileOutputStream(pfd.fileDescriptor)` with its `pfd` separately closed in a guarded `finally`; never depend on `FileOutputStream.close()` alone to close `pfd`, and never double-close it as if two independent owners existed. Count bytes; flush; attempt `FileDescriptor.sync()` if supported (an unsupported sync changes durability status, not ciphertext correctness); on success **complete and close the selected owning stream/descriptor exactly once**, and propagate close errors. If streaming/close failure occurs while the `pfd` is still open, call `pfd.closeWithError(sanitizedReason)` **before any normal-success close/EOF**, then close remaining wrappers in `finally` without masking the first error. `closeWithError` can only notify providers that support a reliable peer/error protocol; **it does not guarantee every cloud provider discards the partial document**. Fall back cleanly to `ContentResolver.openOutputStream(uri, "wt")` / `openOutputStream(uri)` if the provider has no descriptor; such streams have no `pfd.closeWithError`, so rely on close-result/readback/cleanup. **Reopen** the URI with `openInputStream` when permitted and stream-hash stored bytes against the verified ciphertext part (`SHA-256` plus exact byte count); a matching readback warrants `ذخیره شد و قابل‌خواندن تأیید شد`, not permanent remote persistence. If unreadable, clearly label `ذخیره شد؛ صحت فایل در مقصد تأیید نشد` and offer verification/retry. On any write, readback-mismatch or close failure, report failure/unverified and query `DocumentsContract.Document.COLUMN_FLAGS` for `FLAG_SUPPORTS_DELETE` before best-effort `DocumentsContract.deleteDocument` (wrapped in `try/catch`); warn when an incomplete external file could remain. The app must never silently overwrite an old backup without a fresh user `ACTION_CREATE_DOCUMENT` selection.
7. **Staging Cleanup & Cold-Start Orphan Sweep:** Delete private snapshot, verification plaintext and partial ciphertext on handled success/cancel/failure. On cold launch call `RestoreRecoveryBootstrapper` **before** staging cleanup; then remove only orphan files not referenced by active journal states. Never touch live SQLite during export. Secure unlink of flash blocks is not guaranteed.
8. **Final Confirmation:** Display a truthful destination-dependent export status, filename, timestamp, encrypted byte size, all-profile scope, and destination label. Explain that shared/cloud file retention is outside the app's guarantee, especially when destination verification was unavailable.

## 6. Restore pipeline — **two-phase and crash-safe**

### Phase A: Read-only validation + preview (zero active DB mutation)

1. **Bounded SAF Ingestion:** User selects `.medbackup` via SAF `ACTION_OPEN_DOCUMENT`. Query `OpenableColumns.SIZE` first: reject an explicitly reported non-negative out-of-range size (`0 <= reportedSize < 4217` or `reportedSize > 67108985`); providers may legitimately return `null` or negative (`< 0`) when size is unknown, in which case proceed only with streaming enforcement. Stream-copy input URI into an unguessably named, app-private encrypted candidate inside `<app_no_backup_dir>/backup_staging/` with a hard cap **`121 + 67108864 = 67108985` bytes** (which already includes the 16-byte GCM tag). Reject early EOF against a known declared size and mismatches between actual and authenticated declared lengths. Clean up on failure. Never pass a `content://` URI to SQLite.
2. **Pre-KDF Framing Check & Authenticated Decryption:** Validate the frame and approved KDF tuple per §§3–4, check RAM headroom and available disk for ciphertext plus staging plaintext and migrations. Use native Argon2id and a reviewed **truly incremental, provider-verified bounded-memory** AES-256-GCM implementation (see §3) that writes any pre-authentication decrypted bytes into a **non-executable, quarantined private staging file only**. Do **not** open, read as SQLite, preview, publish, or migrate decrypted bytes before final GCM tag validation and successful close; a Java GCM `Cipher.update` loop is not sufficient evidence of streaming. Wipe mutable secrets after final use; on bad password/tag close and remove staging best-effort and show `رمز نادرست است یا فایل آسیب دیده` without changing active data.
3. **Hardened SQLite Defensive Validation (Anti-Malicious-DB Gate):** Open `candidate.sqlite` in isolation using `SQLITE_OPEN_READONLY` with defensive flags applied **before** any schema or data query:
   - Open an isolated SQLite native connection with `SQLITE_OPEN_READONLY | SQLITE_OPEN_NOFOLLOW` where supported, `SQLITE_DBCONFIG_TRUSTED_SCHEMA = 0`, `SQLITE_DBCONFIG_DEFENSIVE = 1`, `SQLITE_DBCONFIG_ENABLE_LOAD_EXTENSION = 0`, `SQLITE_DBCONFIG_ENABLE_TRIGGER = 0`, `SQLITE_DBCONFIG_ENABLE_VIEW = 0`. Execute `PRAGMA mmap_size=0`, `PRAGMA cell_size_check=ON`, and `PRAGMA writable_schema=OFF` **prior** to activating the restrictive authorizer callback, then register a native `sqlite3_set_authorizer` callback that permits `SQLITE_SELECT`, `SQLITE_READ`, safe built-in scalar/aggregate `SQLITE_FUNCTION` calls (strictly blocking `load_extension` / tokenizer functions), and only the explicit read-only `SQLITE_PRAGMA` allowlist (`integrity_check`, `foreign_key_check`, `user_version`, `page_size`, `page_count`, `table_info`, `index_list`, `index_info`, `foreign_key_list`), while denying `SQLITE_ATTACH`, `SQLITE_DETACH`, and all write/DDL operations. Verify each required capability is actually supported by the bundled SQLite runtime; reject if a critical safety setting or authorizer cannot be applied. Never use the ordinary Drift app connection for this untrusted file.
   - Obtain `PRAGMA page_size` and `PRAGMA page_count` as **two separate integer queries** (or documented table-valued `pragma_page_size()`/`pragma_page_count()`), multiply with checked 64-bit arithmetic, and verify that declared database pages fit the actual authenticated file and `<= 67108864` bytes. **`PRAGMA page_size * PRAGMA page_count` is invalid SQL.** File size alone is not a guarantee against SQLite parser bugs; configure SQLite memory/row/time limits and run defensive checks in a bounded worker.
   - First execute `PRAGMA integrity_check(10)` and demand exactly one `ok` result; then `PRAGMA foreign_key_check` must return zero rows and `PRAGMA user_version` must match the **authenticated** header.
   - Inspect `sqlite_master` (universal across all SQLite versions), table/column declarations, indices, foreign keys, uniqueness constraints and accepted internal SQLite objects (`sqlite_sequence` and `sqlite_autoindex_*` where generated by schema constraints). Compare against **version-specific, generated and fixture-verified allowlists** for v1–v5 (or reject `1..4` if historical fixtures are not yet pinned; see §10 Item 1), never a v5-only whitelist applied to historical backups. Reject unknown triggers, views, virtual tables or unknown schema objects; do not execute attacker-provided schema SQL or enable loadable extensions.
4. **Staged Schema Migration (v1..v4 → v5):** If source schema is v1..v4, first pass the **source-version** defensive schema gate. Clone the fully authenticated candidate to a dedicated private migration workspace; only then open **that copy** in isolated write mode with verified defensive settings (`trusted_schema = OFF`, `defensive = ON`), a strict SQLite authorizer permitting **only source-version-specific, fixture-tested generated migration statements** (`SELECT`, `READ`, safe functions, required table/index DDL and DML, required `PRAGMA` operations) while strictly denying `SQLITE_ATTACH`, `SQLITE_DETACH`, `CREATE TRIGGER`, `CREATE VIEW`, `CREATE VIRTUAL TABLE` and extensions. **Decide and verify `PRAGMA foreign_keys=ON/OFF` before entering `BEGIN` or a `SAVEPOINT`**, because changing it *inside* a transaction is a SQLite no-op; document each historical migration's required setting and prohibit silently proceeding on a mismatch. Execute the verified `AppDatabase` v1..v4 → v5 migration chain **inside a single transaction** without invoking `beforeOpen` production side effects or timers, and prove atomic rollback on a deliberately failed intermediate step. Re-enable/verify foreign-key enforcement **after** transaction completion if disabled, run `PRAGMA foreign_key_check` (zero rows), then close the isolated connection cleanly and rerun ALL v5 read-only defensive checks against generated v5 fixtures. If Drift's actual `Migrator.alterTable` emits additional SQL, explicitly fixture-approve those exact operations rather than broadly lifting the authorizer. Some legitimate migrations may need trusted features; narrowly justify and test any exception against hostile legacy fixtures. If safe migration cannot be verified, reject that legacy source version without touching active data.
5. **Side-by-Side Comparison Preview, Stable Source & Dual Confirmation:** Query bounded summary counts from the **validated, migrated v5 staging copy** and the current live DB (profiles, medications, dose events, stock ledger entries, health measurements, visits, tasks, questions). At the **same consistent read transaction** as the current-data preview, compute a **deterministic logical-data fingerprint** over all 17 application tables and their rows, **plus `sqlite_sequence` if `sqlite_sequence` exists in `sqlite_master`** (schema/version plus unambiguous type/length-encoded values ordered by a stable complete key). `sqlite_sequence` holds AUTOINCREMENT high-water marks that can change even if rows currently visible in the application tables do not (and is omitted deterministically when SQLite has not created `sqlite_sequence`). Do not log plaintext or hashes of individual health records. Hashes of SQLite file bytes alone are unsuitable because WAL/checkpoints/VACUUM may alter bytes without changing the data. Retain the full fingerprint and current row counts **in memory** for that one preview/confirmation session, and calculate the candidate SHA-256 from the validated v5 staging file. Explain **full replacement, not merge**, including effects on profiles, today's reminders and data added since the backup. Require an explicit understanding checkbox plus a separate destructive confirmation action (`جایگزینی کامل اطلاعات`). Cancelling, leaving the preview, process restart or navigating back invalidates consent and wipes only non-journal-owned staging. No live DB/alarm mutation occurs in Phase A.

### Phase B: Controlled atomic replacement after explicit confirmation

6. **Preflight, Freeze and Verified Drift/SQLite Closure:**
   - Compute worst-case file-space requirements from **actual** live DB, WAL, immutable rollback, staged/migrated candidate, same-directory install temporary copy (`install.ready`), journal and +16 MiB margin; validate `StatFs` and repeat the check immediately before file creation. A heuristic `3 × max(...)` is not a substitute for calculating these concurrently existing files.
   - Acquire the exclusive cross-service `DatabaseLifecycleLock`, **implemented on a verified native/OS-backed lock that serializes separate Dart isolates, Flutter engines and any declared Android processes** (e.g. a correctly tested app-private file lock with explicit owner/lifetime semantics; never merely a Dart static mutex). All ordinary SQLite/Drift sessions must acquire a compatible **lifetime-held admission lease** before opening `AppDatabase` or a native handle; the exclusive restore/recovery owner must block new admission and wait for every pre-existing lease to be released **after handle closure**, not merely do a momentary file-existence check. Background response handlers obey the same gate or fail closed. Freeze actual profile/medication/stock/health/care writes, callbacks, streams and reminder coordinators. Drain in-flight transactions and prevent new ones; **do not assume Riverpod or WorkManager exists**. Keep the exclusive lock across comparison, reminder cancellation, WAL checkpoint, file swap and state verification. Distinguish native lock ownership from journal/pending-flag disk state; loss of the process lock on crash must not permit a new entrypoint to bypass durable recovery.
   - **Before creating the reconcile marker, cancelling any alarm, checkpointing WAL or touching journal/active files**, recompute the exact Phase A logical-data fingerprint under the frozen/quiesced DB and verify that it equals the preview fingerprint; separately verify the v5 candidate file's size and SHA-256 against the preview candidate. If either differs, release locks, discard confirmation and require a new side-by-side preview and fresh dual consent; no replacement or reminder mutation is permitted. The comparison remains bounded by the v1 `64 MiB` candidate limit; on insufficient space/time for safe verification, fail closed.
   - **Only after both fingerprints match**, durably create the `fsync`-committed pending-reconciliation marker `<app_no_backup_dir>/backup_journal/reconcile_pending.flag` (`operation_id`, `db_generation`, checksum) **before canceling any managed Android alarm**. Cancel the app's existing medication/care alarms; rollback/relaunch must eventually rebuild them. Warn that a hard stop can temporarily suspend reminders until the next app or supported recovery launch.
   - On the **last** live DB connection issue `PRAGMA wal_checkpoint(TRUNCATE)` and parse the returned busy/log/checkpointed counters; abort replacement on incomplete/busy checkpoint. Await `AppDatabase.close()` and all other native/Drift sqlite handles and isolate lifetimes using instrumented lifecycle APIs; use `/proc/self/fd` only as an additional Android diagnostic, **not** the sole ownership proof. Stop safely on timeout or unknown open connection. After confirmed closure only, ensure no uncheckpointed `-wal` frames remain. `-shm` is an ephemeral index, **not** a recoverable data file; if a hot `-journal`/other unexpected sidecar is observed, recover it safely under SQLite or abort rather than deleting it blindly.
7. **Durable Restore Journal & Canonical Immutable Rollback:**
   - Resolve the actual app database path and private journal/staging/rollback paths under `<app_no_backup_dir>/backup_journal/`, `<app_no_backup_dir>/backup_staging/`, and `<app_no_backup_dir>/backup_rollback/`. Verify **same filesystem device ID (`st_dev`) for all rename source/target paths**, no symlink traversal, app-private mode/ownership, and durable directory `fsync` support using native adapters. **Never** infer same-volume safety merely from `/data/user/0/...` text. All journal/file operations must be serialized and idempotent.
   - Journal file `<app_no_backup_dir>/backup_journal/restore_journal.json` contains `journal_version = 1`, `operation_id`, schema v5, selected `backup_id`, `old_absent` flag, previous database size/SHA-256, candidate size/SHA-256, expected paths (strict internal allowlist), `state`, and `journal_sha256` (canonical SHA-256 digest over all preceding fields against torn/corrupt journal writes); never store passwords, keys or medical data. Persist each state by `write unique .tmp -> fsync(file) -> atomic rename over restore_journal.json -> fsync(parent directory)` and check every error. A corrupted journal (`journal_sha256` mismatch or parse failure) or ambiguous file set must **block normal DB startup and expose recovery-only UI**, never default to creating a new empty DB.
   - Durably persist `PREPARED` **before any active DB path mutation**. After confirmed clean WAL checkpoint/closure, copy the clean main DB into immutable `<app_no_backup_dir>/backup_rollback/old_db.master` (or durably record `old_absent = true` on genuinely fresh installation where no active DB file exists), `fsync` and independently validate the complete rollback copy (integrity, FK, schema, SHA-256, size); then durably advance to `OLD_SAVED`. **Never move, truncate, rename away or delete `old_db.master` while rollback/recovery may still need it.** Do not copy non-empty `-wal`/`-shm` files into a file named `.sqlite`.
8. **Atomic Install, Durable Commit and Cleanup:**
   - Copy the **verified v5 candidate** into a new same-directory `install.ready` file with app-only permissions, `fsync(file)` and `fsync(directory)`; keep candidate and `old_db.master` intact during install. With every writer and sqlite handle closed, remove *only* the confirmed checkpointed, inactive `-wal`/`-shm` sidecars; handle hot `-journal` by SQLite recovery or abort, never blind unlink. `fsync(directory)`, then atomically rename `install.ready` **over** the existing main DB name (single-filesystem POSIX replace, no separate delete of main DB). `fsync` the DB directory. A crash before journal advancement to `NEW_INSTALLED` is conservatively handled as `OLD_SAVED` rollback.
   - Durably record `NEW_INSTALLED`, open/verify the installed DB (defensive schema/integrity/FK/user_version checks and core read-only repository smoke queries), then record `VERIFIED`. **Re-close all verification SQLite handles** before any possible rollback file operation.
   - Once installed data is valid, durably record `COMMITTED` **BEFORE** deleting `old_db.master` or candidate staging. Then cleanup rollback and unused staging, with `fsync` of affected parent directories, then unlink `restore_journal.json` and `fsync` its directory. If cleanup fails, leave `COMMITTED` journal for retry on next boot; do not show failure to save the dataset merely because a harmless orphan cleanup failed. Never delete canonical rollback in the `VERIFIED` state prior to durable commit.
9. **Pre-Open Crash Recovery Protocol (`RestoreRecoveryBootstrapper`):**
   - After `WidgetsFlutterBinding.ensureInitialized()` (necessary for Flutter platform channels), but **before `runApp`, `AppDatabase`, repository initialization, notifications or any worker opens SQLite**, the primary application entrypoint obtains the **exclusive native lifecycle/recovery lock** and executes `await RestoreRecoveryBootstrapper.runBeforeAppStart()` exactly once as authoritative recovery owner per startup attempt. The state machine remains retryable across process deaths via its durable journal. Every additional Dart headless `@pragma('vm:entry-point')` entrypoint must run a **native/FFI recovery-complete admission guard before opening SQLite**: if the main owner is recovering, a journal remains, a pending transition is ambiguous, a native lock cannot be acquired/verified, or required headless plugin channels are unavailable, it must **defer/drop DB-dependent work without constructing `AppDatabase`**, and arrange a safe subsequent retry. It must **not independently start concurrent journal recovery under a Dart singleton**. Once recovery is durably complete, that entrypoint may hold a compatible native database-session lease for its SQLite handle lifetime, and only then process safe, idempotent actions. In the event of an unresolved journal, suppress normal app startup until verified/recovered. **Only after** journal handling may orphan staging sweep run. Implement a recovery-only UI for unresolvable cases; never initialize an empty DB as fallback.
   - Recovery matrix, applied repeatedly if recovery itself crashes:
     - `PREPARED`: No active-path replacement may have begun; verify the existing DB or the declared `old_absent` condition, remove any stray `install.ready` / `old_reinstall.ready` temporary files, preserve unexplained artifacts for diagnosis, remove only proven orphans, and clear the journal durably.
     - `OLD_SAVED`: Treat the main DB as potentially replaced. First remove any stray `install.ready` / `old_reinstall.ready` temporary files in the active DB directory.
       - If `old_absent == false`: Validate `old_db.master` **before touching the active path**; copy it to `old_reinstall.ready` and `fsync` this temporary file. Ensure no SQLite handle can access the active path; if an unexpected hot `-journal` exists, stop and recover safely rather than deleting it. **Before installing the rollback DB**, remove only previously verified inactive WAL/SHM sidecars from the active directory and `fsync` that directory; then atomically rename `old_reinstall.ready` over the active DB and `fsync` the directory again. **Never** leave a window where an old DB has been renamed into place but incompatible new-DB WAL remains. Verify the restored active DB only after the sidecar cleanup has durably completed. Keep `old_db.master` throughout. If recovery crashes at any copy/delete/fsync/rename/state step, the next boot can safely repeat from that immutable master; on unexpected handles or uncertain sidecar ownership, fail closed. Persist `ROLLED_BACK` durably **before** cleanup.
       - If `old_absent == true`: If the active DB file does not exist, advance durably to `ROLLED_BACK` and clean up; if the active DB file *does* exist and matches `journal.candidate_sha256` and `journal.candidate_size` (with no stray WAL/SHM sidecars), the atomic rename completed right before process death—advance durably to `NEW_INSTALLED` and execute the `NEW_INSTALLED` verification path; if it exists with a mismatched hash or unexpected sidecars, halt with recovery-only UI instead of deleting an uncertain active file.
     - `NEW_INSTALLED`: Remove any stray `install.ready` / `old_reinstall.ready` files; validate the installed new DB. If valid, advance through `VERIFIED` and durable `COMMITTED`; if invalid and `old_absent == false`, invoke the same **retryable** rollback procedure from `old_db.master`, then record `ROLLED_BACK` (or halt with recovery-only UI if `old_absent == true` and validation fails).
     - `VERIFIED`: **Re-verify** new DB if journal remains; on failure and available validated master, rollback; on success persist `COMMITTED` before any master deletion.
     - `COMMITTED`: Verify installed DB before allowing normal boot, finish idempotent cleanup and reconcile alarms. If DB fails verification and a valid rollback master still exists, retryable rollback is allowed; if neither valid copy is available, **stop with recovery-only UI** and retain artifacts. Do not silently clear a damaged journal or create a new DB.
     - `ROLLED_BACK`: Verify the old active DB (or confirmed `old_absent` fresh state); if corrupt and immutable master still exists, retry; otherwise finish cleanup durably, show interrupted-restore notice, and request idempotent alarm reconciliation on startup.
   - On any impossible state, missing master, torn/checksum-invalid journal, failed `fsync`, failed SQLite verification, or inability to prove safe sidecar/handle closure, **halt destructive operations**, retain remaining files, and display a recoverable diagnostic/support path without PII.
10. **Post-Recovery Data and Notification Reconciliation:**
    - On successful installation **and after every rollback or journal recovery**, reinitialize actual repositories/coordinators. **Consume (unlink + `fsync` parent dir) `<app_no_backup_dir>/backup_journal/reconcile_pending.flag` created before alarm cancellation only after schedules were fully rebuilt or the denied-permission state was truthfully persisted.** Keep the marker across process death and retries; if alarms were not cancelled yet, the rebuild must still be idempotent. Cancel only managed legacy notification IDs and deterministically rebuild schedules for active profiles/current clock and timezone; never duplicate historical `DoseEvents` or stock movements. Avoid firing old overdue doses. If an uncanceled OS alarm fires or is tapped during an interrupted window prior to reboot, its background entrypoint **must obtain the native recovery-complete guard and a lifetime-held DB admission lease**; otherwise **suppress/defer the database side effect** and rely on the authoritative main-start recovery and reconciliation. It must never race its own uncoordinated `RestoreRecoveryBootstrapper` instance. If the app is force-stopped and never reopened, Android may not deliver app reminders until relaunch; show this limitation honestly.
    - Compute low-stock/expiry status from **existing v5 inventory tables and stock rules**; do not require nonexistent `AlertInstance`/persisted `DoseOccurrence` tables. Android notification scheduling is **not atomic with SQLite**; a crash may temporarily leave reminders absent, and an idempotent startup/boot reconciliation path must repair them. Respect disabled `POST_NOTIFICATIONS`/exact-alarm permissions and explicitly distinguish data recovery from notification availability.
    - **Native boot receiver gate (verified against plugin 23.0.2 source):** On `BOOT_COMPLETED`, `MY_PACKAGE_REPLACED` and other broadcast actions already handled by the original plugin receiver, register only `SafeScheduledNotificationBootReceiver`. It synchronously inspects the journal/marker files and their expected private paths. If either exists, is ambiguous, or cannot be safely read (including locked Credential-Encrypted storage), **do not dispatch** the underlying plugin receiver. If safe (both absent), delegate to the publicly accessible `new ScheduledNotificationBootReceiver().onReceive(context, intent)`; **do not call** `FlutterLocalNotificationsPlugin.rescheduleNotifications(context)` from the app package because this static method is package-private. Keep the class imported from the pinned plugin but ensure its receiver is not separately registered in the final merged manifest; maintain original intent actions and `android:exported` policy. 11. **Completion and Privacy-Aware Local Audit:**

## 7. Android platform backup privacy gate

Current `android/app/src/main/AndroidManifest.xml` contains no explicit `android:allowBackup` or `android:dataExtractionRules`. Android's `allowBackup` defaults to `true` on typical Android versions; sensitive local SQLite might be transferred by the OS independently of the app's password-protected backup feature. The feature owner must choose and test a privacy policy before public beta.

**Proposed v1 policy:**
1. Once manual encrypted export is working and the user has seen a clear retention warning, disable implicit Android cloud backup and device-to-device (D2D) transfer for app-private health data by setting `android:allowBackup="false"`, `android:fullBackupContent="@xml/backup_rules"` (Android 11 and below), and `android:dataExtractionRules="@xml/data_extraction_rules"` (Android 12+, explicitly excluding both `<cloud-backup>` and `<device-transfer>` domains for `database`, `file`, `sharedpref`, and `external`).
2. Store all backup staging, rollback, and journal artifacts inside Android's `getNoBackupFilesDir()` (`no_backup/`), which the Android OS excludes from backup agents by design.
3. Because Android 12+ OEM device-to-device transfer behaviors can vary across manufacturers, verification on target devices/emulators is mandatory. This is a privacy hardening measure, **not** proof the live DB is encrypted at rest. Do not silently disable recovery paths before informing test users of possible data loss on uninstall.

## 8. Test matrix (automated unless labeled DEVICE)

**Crypto / binary format:**

1. AES-256-GCM known test vectors and round-trip; output differs for repeated export of identical content.
2. Fresh independent 16-byte salt + 12-byte nonce for 1000 back-to-back exports; uniqueness verification (statistical + mocked RNG boundary tests).
3. Wrong password produces no **accepted/authenticated** plaintext, never opens decrypted staging as SQLite, removes best-effort partial private output, and makes zero active-DB/alarm mutations.
4. Flip a single bit in magic, version, header fields, reserved flags, length, ciphertext, or 16-byte GCM tag; every variant rejects before any staging SQLite inspection or restore write.
5. Truncated header, trailing bytes after tag, invalid `app_id`, unsupported `cipher_id`/`kdf_id`/`envelope_version`, non-zero `reserved_flags`, out-of-range `created_utc_epoch_ms` (`<= 0` or `> 8640000000000000` Dart `DateTime` overflow), sub-4096-byte payload, and unsigned-64-bit high-bit overflow lengths (`>= 2^63`) reject cleanly prior to KDF without `RangeError`.
